src/
└── lib/
    └── projects.ts         ← getProject/getProjects are async (session 6)

Every single file in this project so far is a **Server Component** — including
the `async function ProjectPage` that awaits `getProject(slug)`. We never
noticed because nothing needed a directive. Today: what that default actually
means, and when it stops being enough.

---

## Key idea: Server Components are the default, not a mode you opt into

In the App Router, **every component is a Server Component unless you say
otherwise**. That's why `ProjectPage` can be `async` and `await` data directly
— something a normal React component has never been able to do. Server
Components run once, on the server, produce HTML (+ a serialized description
of the React tree), and ship **zero JavaScript** for that component to the
browser.

Consequences you've already benefited from without naming them:

| What you did | Why it worked |
|---|---|
| `await getProject(slug)` directly in the component body | Server Components can be `async` functions |
| No `useState`/`useEffect` anywhere yet | Haven't needed interactivity yet |
| `notFound()` inside `page.tsx` | Works during server render, before any HTML is sent |
| Bundle stays small as pages grow | Server Component code never ships to the client |

## Step 1. What a Server Component *can't* do

Try (mentally, or actually paste it in) adding this to `app/about/page.tsx`:

```tsx
export default function AboutPage() {
  const [count, setCount] = useState(0); // ❌
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

This fails at build/runtime: `useState` and `onClick` both require the
component to run **in the browser**, re-render on state changes, and attach
real DOM event listeners. A Server Component only ever runs once, on the
server — there's no "later" for it to re-render in.

Rule of thumb — you need a Client Component the moment you need:
- `useState`, `useEffect`, `useContext`, any hook with client-side lifecycle
- Event handlers (`onClick`, `onChange`, ...)
- Browser-only APIs (`window`, `localStorage`, `IntersectionObserver`, ...)

---

## Step 2. Opting in with `'use client'`

`'use client'` at the top of a file doesn't mean "this runs only in the
browser" — it means **"this component (and everything it imports) gets
bundled and hydrated in the browser too."** It still renders on the server
first for the initial HTML, then hydrates client-side.

A minimal example — a copy-to-clipboard button on the project detail page:

```tsx
// src/components/CopySlugButton.tsx  ← illustrative, not yet added to the repo
'use client';

import { useState } from 'react';

export function CopySlugButton({ slug }: { slug: string }) {
  const [copied, setCopied] = useState(false);

  return (
    <button
      onClick={() => {
        navigator.clipboard.writeText(slug);
        setCopied(true);
      }}
      className="text-xs underline text-zinc-500"
    >
      {copied ? 'Copied!' : 'Copy slug'}
    </button>
  );
}
```

This is exactly why `error.tsx` needed `'use client'` in session 6: error
boundaries are implemented with `componentDidCatch`, a class-component
lifecycle method — which only exists in components that run (and re-render)
in the browser.

## Step 3. The boundary is a one-way door

There are two different "nesting" directions here — only one of them is
actually forbidden:

| Importer ↓ / Renders → | Server Component | Client Component |
|---|---|---|
| **Server Component** | ✅ normal | ✅ normal (this *is* opting into client) |
| **Client Component** | ❌ **not directly** | ✅ normal |

The only broken cell: a `'use client'` file that `import`s a Server
Component's file and renders it as a plain JSX tag inside itself.

### Why it breaks

```tsx
// Modal.tsx
'use client';
import { ProjectDetails } from './ProjectDetails'; // ProjectDetails is a Server Component

export function Modal({ isOpen }: { isOpen: boolean }) {
  const [open, setOpen] = useState(isOpen);
  if (!open) return null;
  return (
    <div className="modal">
      <ProjectDetails /> {/* ❌ */}
    </div>
  );
}
```

`Modal.tsx` has `'use client'` — meaning everything it imports also has to
ship to the browser. But `ProjectDetails` might do `await db.query(...)` or
read a server-only secret — code that can't run client-side at all. Next.js
either errors at build time or strips the server-only capability; either way,
it's not the pattern you want.

### The escape hatch: composition via `children`

```tsx
// page.tsx — Server Component (the parent)
import { Modal } from './Modal';
import { ProjectDetails } from './ProjectDetails';

export default async function Page() {
  return (
    <Modal>
      <ProjectDetails slug="nextjs_01" /> {/* rendered HERE, by page.tsx */}
    </Modal>
  );
}
```

```tsx
// Modal.tsx
'use client';
export function Modal({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(true);
  if (!open) return null;
  return <div className="modal">{children}</div>; // just slots in a finished result
}
```

The difference: `Modal.tsx` no longer **imports** `ProjectDetails` — it
doesn't even know what that component is. `page.tsx` (still a Server
Component) already rendered it before handing the result down as `children`.
`Modal`'s client bundle only contains its own `useState` logic — none of
`ProjectDetails`'s server-only work leaks into the browser.

### You already have this pattern in the repo

`app/projects/[slug]/layout.tsx` (the sidebar) does exactly this — it renders
`{children}`, and `{children}` is `page.tsx` below it, also a Server
Component. If that layout got `'use client'` tomorrow (say, a collapsible
sidebar with `useState`), `page.tsx` would keep working unchanged — because
Next.js composes every `layout.tsx` + `page.tsx` pair through `children`
automatically, for every route in the App Router. It's the same rule, just
applied by the framework instead of by hand.

## Step 4. Props crossing the boundary must be serializable

Server → Client props travel over the network as serialized data (like JSON).
Strings, numbers, booleans, plain objects/arrays: fine. Functions, class
instances, `Date` objects passed as-is: not fine (functions specifically —
Server Actions are the one exception, they're compiled into callable
references, covered in Phase 4).

```tsx
// ❌ Server Component passing a function prop to a Client Component
<CopySlugButton onCopy={() => console.log('copied')} slug={slug} />

// ✓ pass data, let the Client Component own its own behavior
<CopySlugButton slug={slug} />
```
