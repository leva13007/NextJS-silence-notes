# Special Files with Real Async

> **Date:** 2026-06-25 | **Session #:** 6 | **Duration:** —
> **Roadmap:** Phase 1 → Special files in context
> **Docs:** [nextjs.org/docs/app/api-reference/file-conventions/loading](https://nextjs.org/docs/app/api-reference/file-conventions/loading) · [error.js](https://nextjs.org/docs/app/api-reference/file-conventions/error)
> **Stream:** ⬜ Not streamed ([YouTube link])

Session 5 showed `loading.tsx` with an artificial `setTimeout`. The problem: `getProject`
is synchronous — the page component resolves instantly, so `loading.tsx` never actually
fires in that case. Today we fix that by making data fetching genuinely async, then add
`error.tsx` to handle runtime failures.

---

## Starting point

```
app/
├── layout.tsx
├── page.tsx
├── globals.css
├── about/
│   └── page.tsx
└── projects/
    ├── page.tsx
    ├── not-found.tsx
    └── [slug]/
        ├── layout.tsx
        ├── loading.tsx          ← exists but never fires (sync data)
        └── page.tsx             ← calls getProject() synchronously
src/
└── lib/
    └── projects.ts              ← getProject() is sync, returns immediately
```

Goal: make `getProject` async → `loading.tsx` fires for real → add `error.tsx`.

---

## Why `loading.tsx` wasn't firing

`loading.tsx` wraps the page in a `<Suspense>` boundary automatically. Suspense only
shows the fallback while a component is **suspended** — i.e., while it's waiting for an
async operation to resolve.

```ts
// src/lib/projects.ts (current — sync)
export function getProject(slug: string) {
  return projects.find((p) => p.slug === slug) ?? null; // instant
}
```

`getProject` returns immediately. The component never suspends. `loading.tsx` is
registered but never triggered.

The `await new Promise(setTimeout)` from session 5 was a workaround — it made the
component itself wait. But the real pattern is: fetch data, and let the async operation
do the waiting.

---

## Step 1. Make `getProject` async

```ts
// src/lib/projects.ts — add async, simulate latency
export async function getProject(slug: string) {
  await new Promise((r) => setTimeout(r, 800)); // simulates DB / API call
  return projects.find((p) => p.slug === slug) ?? null;
}
```

The delay is still fake, but the shape is now correct: an async function that returns a
`Promise`. In a real app this would be `fetch()`, a Prisma query, etc. — the page
suspends while the Promise is pending, and `loading.tsx` shows automatically.

---

## Step 2. Await `getProject` in the page

```tsx
// app/projects/[slug]/page.tsx
- const project = getProject(slug);       // was sync, returned value directly
+ const project = await getProject(slug); // now async, must await
```

The component is already `async` (needed for `await props.params`), so no other change
is needed. The rest of the component — `notFound()`, JSX — stays the same.

Now navigate to a project in the browser. You'll see:
1. Sidebar renders immediately (prefetched layout)
2. "Loading project…" appears for ~800 ms
3. Project content renders

That's `loading.tsx` firing from real async — not a workaround.

## Step 3. Add `error.tsx`

`error.tsx` is an **Error Boundary** for a route segment. When the page component
throws during render, Next.js catches it and renders `error.tsx` instead.

```tsx
// app/projects/[slug]/error.tsx  ← NEW FILE
'use client'; // required — error boundaries must be Client Components

export default function ProjectError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div className="flex flex-col flex-1 items-center justify-center gap-4 font-sans">
      <h2 className="text-xl font-bold text-red-500">Something went wrong</h2>
      <p className="text-zinc-500 text-sm">{error.message}</p>
      <button onClick={reset} className="text-sm underline">
        Try again
      </button>
    </div>
  );
}
```

### Why `'use client'`?

Error boundaries use `componentDidCatch` under the hood — a React lifecycle method
that only exists in class components. Next.js wraps your `error.tsx` in one internally,
but the file itself must be a Client Component for React to wire it up correctly.

### Props

| Prop | Type | What it is |
|------|------|------------|
| `error` | `Error & { digest?: string }` | The thrown error. `digest` is a server-side hash (logged in server output) that maps to the original error without leaking details to the client. |
| `reset` | `() => void` | Re-renders the route segment — lets the user retry without a full page reload. |

### Triggering it temporarily

To see `error.tsx` in action, throw inside the page:

```tsx
// app/projects/[slug]/page.tsx — temporary
throw new Error('test error');
```

Navigate to any project — you'll see the error UI with the "Try again" button. Remove
the throw after confirming.

## Step 4. `notFound()` is not an error

`notFound()` and `throw new Error()` look similar but go to completely different places.

```
throw new Error('...')   →  caught by error.tsx  →  shows error UI
notFound()               →  NOT caught by error.tsx  →  shows not-found.tsx
```

`notFound()` from `next/navigation` throws a special internal Next.js signal
(`NEXT_NOT_FOUND`). Next.js intercepts it before the error boundary sees it and
renders the nearest `not-found.tsx` instead. The error boundary is bypassed entirely.

This distinction matters in the page:

```tsx
// app/projects/[slug]/page.tsx
const project = await getProject(slug);

if (!project) notFound(); // → not-found.tsx (expected missing resource)

// if getProject threw during the fetch → error.tsx (unexpected failure)
```

Use `notFound()` for expected "resource doesn't exist" cases. Let unexpected failures
(network errors, DB errors) propagate naturally — they'll hit `error.tsx`.

## Final structure

```
app/
└── projects/
    ├── not-found.tsx            ← renders when notFound() is called
    └── [slug]/
        ├── layout.tsx
        ├── loading.tsx          ← Suspense fallback while page awaits data
        ├── error.tsx            ← Error boundary (new)
        └── page.tsx
src/
└── lib/
    └── projects.ts              ← getProject is now async
```

Three special files, three different triggers:

| File | Trigger | Must be client? |
|------|---------|-----------------|
| `loading.tsx` | Page component suspends (async operation pending) | No |
| `error.tsx` | Page component throws an unhandled error | **Yes** |
| `not-found.tsx` | `notFound()` is called | No |

## Checklist

- [ ] `loading.tsx` only fires when the component suspends — sync data = no suspense = no loading UI
- [ ] Making `getProject` async gives `loading.tsx` a real reason to show
- [ ] `error.tsx` must be `'use client'` — error boundaries are a React class component mechanism
- [ ] `error.reset()` re-renders the segment without a full page reload
- [ ] `notFound()` bypasses `error.tsx` entirely — it's a routing signal, not a runtime error
